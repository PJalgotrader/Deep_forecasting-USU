PyCaret stopped working on Colab. Here is the fix.

Google Colab moved to Python 3.13. The official pycaret package refuses to run on anything newer than 3.11. This guide shows what we tested, why the course now installs the community fork pycaret-core, and the three supported ways to run every PyCaret notebook in the course.

The short version

Install this instead of pycaret:

pip install pycaret-core "statsmodels<0.15" lightgbm xgboost catboost

Same import pycaret, same TSForecastingExperiment, same setup / create_model / compare_models / plot_model. Nothing else in the notebooks changes.

  • Official pycaret 3.3.2 (April 2024) hard-codes a check that raises RuntimeError on Python 3.12 or newer. Colab is on 3.13. The upstream request for 3.12 support was closed as "not planned".
  • pycaret-core 3.5.0 (August 2026) is the community fork maintained by the sktime organisation. It keeps the PyCaret 3 API and supports Python 3.10 to 3.14. It is a drop-in replacement.
  • pycaret 4.0 (alpha) is a redesign. It renames the experiment class and removes plot_model, check_stats and the functional API. Every course notebook would need rewriting, so we are not going there yet.
  • One temporary pin: statsmodels<0.15. Without it, create_model('ets') fails. Details below.

The symptom

The old install cell from the notebooks does this on Python 3.12:

# Python 3.12 (local test)
$ pip install pycaret==3.3.2      # succeeds, 104 packages
$ python -c "import pycaret"
RuntimeError: ('Pycaret only supports python 3.9, 3.10, 3.11.
  Your actual Python version: ', sys.version_info(major=3, minor=12, ...),
  'Please DOWNGRADE your Python version.')

The package installs, because its metadata only says Requires-Python >=3.9. The refusal lives in pycaret/__init__.py and fires at import time. On Colab's actual Python 3.13 it is worse: pycaret 3.3.2 pins numpy<1.27, and there are no numpy 1.26 wheels for 3.13, so pip tries to compile numpy from source and the install cell never finishes.

Check your Python before trusting any docs. Colab's public runtime table still lists Python 3.12 as the latest, but a fresh runtime on 2026-09-16 reported 3.13.15. Run import sys; print(sys.version) first.

What pycaret-core actually pins

The fork has two dependency branches, and the one you get depends on your Python version. This is why the course standardises on 3.13.

On Python 3.12 the fork would drag Colab's numpy 2 and scikit-learn 1.6 back to 2023-era versions and force a runtime restart. On 3.13 it leaves Colab's preinstalled stack untouched. Either way, sktime jumps from 0.26 to 1.1.

Why not 4.0 today

The maintainers describe 4.0 as a redesign, not an increment. From their own status document: the functional API is gone, TSForecastingExperiment became TimeSeriesExperiment, and plot_model, evaluate_model, check_stats, interpret_model, get_leaderboard and automl are removed with "use plotly / sktime / statsmodels directly" as the migration advice. Time series support is an optional extra. On Colab it also conflicts with the notebook's own ipython pin. The first cell of every course notebook fails:

>>> from pycaret.time_series import *
>>> exp = TSForecastingExperiment()
NameError: name 'TSForecastingExperiment' is not defined

The ETS trap and the one pin

With the fork installed and no pin, the very model Module 3 is built around fails:

>>> exp.create_model('ets')
TypeError: ETSResults.simulate() got an unexpected keyword argument 'random_state'

Three things lined up. statsmodels 0.15.0 (2026-08-27) renamed the random_state argument of ETSResults.simulate to rng. sktime 1.1.0, which pycaret uses for every forecaster, still passes random_state when it builds prediction intervals. And nothing in the fork's dependency tree caps statsmodels, so a fresh install picks up 0.15.0. Colab preinstalls 0.15.0 too.

sktime merged the fix on 2026-09-13, but its latest release, 1.1.0, predates it. Until a newer sktime ships, the pin does the job:

signature, 0.14.6
simulate(nsimulations, anchor, repetitions, random_errors, random_state)
signature, 0.15.0
simulate(nsimulations, anchor, repetitions, random_errors, rng)
fix
pip install "statsmodels<0.15", which resolves to 0.14.6
drop the pin when
sktime releases a version newer than 1.1.0 that includes PR 10972, and the smoke test passes without it

A subtle point worth showing students: compare_models does not raise. It silently drops ETS from the leaderboard when the model errors, so the failure only shows up in create_model, or as a missing row.

The stale-runtime trap

This one caught us during testing and will catch students. Run the install cell in a Colab session where pycaret has already been imported, and the newly installed model libraries never show up:

>>> exp.compare_models(include=[..., 'catboost_cds_dt'])
ValueError: Estimator catboost_cds_dt Not Available.

pycaret checks its optional model libraries once, at first import, and caches the answer. Installing catboost afterwards in the same kernel changes nothing, even after importlib.invalidate_caches(). A fresh interpreter sees it immediately. Two rules follow:

  • Install everything before the first import pycaret.
  • On Colab, start from Runtime → Disconnect and delete runtime, then Run all. The tell-tale sign of a stale runtime is the "before install" cell already listing pycaret-core, or execution counters that do not start at 1.

How to run the notebooks

Three supported ways. All of them give you the same stack: Python 3.13, pycaret-core 3.5.0, statsmodels<0.15, lightgbm, xgboost, catboost. Pick one.

1 · Google Colab

Zero install, any laptop

The notebooks now carry an install cell that runs only on Colab. Start from a fresh runtime and run it first.

!pip install -q pycaret-core \
  "statsmodels<0.15" \
  lightgbm xgboost catboost

2 · uv

Local work, exact reproducibility

The repository root is a locked uv project covering Modules 2 to 5. 180 packages pinned; everyone gets identical versions.

cd Deep_forecasting-USU
uv sync
uv run jupyter lab

3 · conda

Already on Anaconda

An environment file in python_migration/conda. Same pins, installed with pip inside the env.

cd python_migration/conda
conda env create -f environment.yml
conda activate df_pycaret
jupyter lab

VS Code

Both local options work in VS Code with the Python and Jupyter extensions. For uv, register the environment once as a named kernel, then choose it from Select Kernel → Jupyter Kernel in any notebook:

uv run python -m ipykernel install --user --name deep-forecasting --display-name "Python 3.13 (Deep Forecasting)"

For conda, VS Code discovers df_pycaret on its own under Select Kernel → Python Environments.

FAQ

Can I keep using pycaret 3.3.2 locally?

Yes, on Python 3.11 or older. The 2024 conda environment still passes every test. It just cannot be the Colab path, and the last Python 3.11 Colab runtime has aged out of Colab's one-year window.

Do I have to uninstall pycaret before installing pycaret-core?

In a fresh environment there is nothing to uninstall. In an existing one, yes: both packages install into the same pycaret import namespace, and two copies on top of each other is undefined behaviour.

Why Python 3.13 and not 3.12?

Because of the fork's two dependency branches. On 3.12 it pins numpy below 2 and scikit-learn below 1.5, which fights with everything else in a modern environment, including the course's Nixtla notebooks. On 3.13 it uses current versions. It also matches Colab.

When does the statsmodels pin go away?

When sktime publishes a release newer than 1.1.0 containing PR 10972. Test by removing the pin from pyproject.toml, running uv lock --upgrade-package sktime --upgrade-package statsmodels, and re-running scripts/check_environment.py, which trains an ETS model on purpose.

What if the fork stalls?

Modules 3, 4 and 5 already have StatsForecast and MLForecast versions of the same lessons. That is the exit path. For now the fork is five weeks into resumed maintenance under the sktime organisation, which is a reasonable bet for a semester.
